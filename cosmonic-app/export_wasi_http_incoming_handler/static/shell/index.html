You can't execute
what you don't have.

A web shell is a small malicious script planted on a web server. It lets an attacker control that server from a browser: they type a command into a hidden page, the server runs it and sends back the result. It's a remote control panel hiding inside your own website, and it keeps working after the original hole is patched.

PersonFacts is a web app with a web shell built in. Its normal pages work as expected, but one URL, /exec?cmd=…&arg=…, takes whatever command and argument you send and runs them on the host. Inside a container, that is the whole server handed over. An attacker can dump credentials and secrets, open a connection back to their own machine, and download the next piece of their toolkit.

Here, the same vulnerable app runs inside a Cosmonic sandbox. It is isolated, and it can use only what it has been explicitly granted; everything else is denied. We changed none of the vulnerable code, and every attack in the demo is fired. Each one hits a wall: there is no shell to call, no filesystem to read, and no network to reach.

This demo shows how a deny-by-default Cosmonic sandbox stops remote code execution (RCE) without needing a patch.

The three building blocks you're watching for

Almost every remote-shell technique combines: (1) an outbound network connection, (2) binding that socket to stdin/stdout/stderr, and (3) spawning a shell. If your sandbox can see any one of those in a context that shouldn't have it, you've got a signal. A Wasm component doesn't have to see them: it was never given any of the three.

1 · network out2 · bind to stdio3 · spawn a shell

bash / shell built-ins

Bash can open a TCP socket itself via its /dev/tcp/<host>/<port> pseudo-device, then redirect a shell's I/O across it. Variants use mkfifo + nc (a named pipe feeding netcat), or nc -e where that flag is compiled in.

Detection signal: a shell process with a socket FD, or /dev/tcp access, or a FIFO wired between two processes.
In this sandbox: there is no bash, sh or nc to start, no /dev to open, and no socket interface to connect with.

python / other interpreters

The canonical pattern is socket → os.dup2 the socket onto fds 0/1/2 → subprocess or pty.spawn a shell. Same shape in Perl, Ruby, PHP, Node.

Detection signal: an interpreter process that both holds a network socket and spawns /bin/sh as a child, especially with dup2/pty in the mix.
In this sandbox: no interpreter to start, no /dev/ptmx for a pty, and WASI has no fork, exec or dup2.

curl / wget (stage-and-run)

The "download something" step: usually stage 1, not the shell itself. The pattern is fetch-then-execute: pipe a remote script straight into an interpreter (curl … | sh), or download to disk and exec.

Detection signal: a network-fetch tool whose output feeds directly into a shell/interpreter, or a freshly written file executed within seconds.
In this sandbox: allowedHosts: [], so the host denies the fetch; there's no disk to stage on and nothing to exec it with.
